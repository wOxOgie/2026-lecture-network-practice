# Week 6 · Observation

## Task 1 · Link state by hand
- Tie-break: heap entries are `(cost, first_hop, node)`, so among equal-cost paths the one leaving by the alphabetically smallest neighbour wins (deterministic). A real OSPF router does not pick one: it installs all equal-cost next hops (ECMP) and hashes flows across them, which I saw in Task 2 (r1 has two `via` lines for `172.20/16`).
- `u → w` goes to **x**, not w: direct `u-w` costs 5, `u-x-y-w` costs 1+1+1 = 3. The table keeps only the first hop and trusts x and y for the rest; sending w traffic out the w interface would be adjacency, not routing.
- After `u-x` fails (costs v 2, x 4, w 5, y 5, z 7), every destination except v moved its hop from x to v; v was already direct. w ties (direct 5 = u-v-w 5) and my rule picks v; OSPF would split over both.

## Task 3 · Reconverge without recomputing the world
- I keep the cost vector `dist` between events (one int per router, ~13 KB for 400, same size as the table). `dijkstra_table` settles nodes in (cost, name) order, so a hop comes from the first tight predecessor (`d[p]+w == d[v]`); if distances and tight links don't change, the table can't.
- All three cases handled: down/dearer on a non-tight link → skip; up/cheaper with `d[a]+w > d[b]` both ways → skip; shorter → push new costs outward locally. Only down/dearer on a node's *only* shortest way in forces a full SPF (176 of 1000). Result: 177 vs 1001 SPF runs = **82% avoided (strong)**, 0 wrong.
- R5: wall 3.17 s vs 1.62 s, because Python bookkeeping costs as much as a Dijkstra step. Still right for a router: the scarce resource is control-plane CPU shared with hellos, flooding and BGP; a flapping link triggers a full SPF on every router at once, a busy router can miss hellos and drop healthy neighbours. In C the bookkeeping is a few memory reads (cf. OSPF incremental SPF / partial route calculation).
