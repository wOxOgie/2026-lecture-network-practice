# Week 3 · Observation

## Task 1 · Iterative resolver
- The root server did not hand me the address because it does not have it: it only knows who runs each TLD. For `www.korea.ac.kr` it answered with zero answers and six `NS` records for `.kr` plus their glue, and I had to walk root → `.kr` (210.101.61.1) → korea.ac.kr (163.152.11.6) — **3 servers**, where my laptop normally asks its resolver **once**.
- Glue-less delegation: `www.prod.ftl.netflix.com` was delegated to `e.ns.nflxso.net` with no glue (the NS is outside the zone, so the parent cannot supply its address). My resolver starts a separate walk from the root for the NS name first (root → .net → nflxso.net), which cost **3 extra queries** (10 in total for one name). Depth is capped (4 nested walks, 20 referrals, 8 CNAMEs).
- `www.microsoft.com` gave me 23.60.186.45 while `dig` gave 104.94.218.45. Both come from the same final name `e13678.dscb.akamaiedge.net`: Akamai picks an edge by who is asking (my machine querying the authoritative server directly vs. my ISP's resolver), so a different address is expected — all 4 stable names matched exactly.

## Task 2 · On the wire, and steering
- Delegation vs. answer, from my capture: they are the same DNS message — frame 36 (root) has answer count 0, six `NS` in AUTHORITY and glue in ADDITIONAL; frame 42 (korea.ac.kr's server) has one `A` in ANSWER. Query frame 41 and response frame 42 share ID 0x7261. The largest response was the root's `.com` delegation (frame 50, 905 bytes: 13 NS + 27 IPv4/IPv6 glue). On the café Wi-Fi no UDP replies came back (frames 1–16 show my resolver trying the next root server each time), so I ran it over TCP; on the hotspot UDP worked.
- My rule: "third party if the CNAME chain ends in a different registrable domain (public-suffix aware, so `bbc.co.uk` not `co.uk`)". It is wrong on **www.wikipedia.org**: the chain ends at `dyna.wikimedia.org`, a different domain but the same owner (Wikimedia runs its own caches) — names cannot show ownership. It is also blind to anycast CDNs with no CNAME, since it never looks at who owns the address.
- Steering number: **7 of 10 CDN-hosted sites answered differently to a different resolver or network** (networks: `KT_PASCUCCI_5G` café Wi-Fi and an SKT phone hotspot). Changing resolver changes a lot (Fastly: 146.75.x from the Korean ISP resolvers, 151.101.x from Google/Quad9). Changing my own network changed only **3 of 10** (the Akamai sites: microsoft, apple, adobe); Fastly sites gave the same 146.75.x on KT and SKT. So claim (b) holds partly: CDNs steer by the *resolver's* location, and KT and SKT in the same city look "nearby" to the same Fastly site.

## Task 3 · Cache
- Two problems with one root cause — the baseline throws away the TTL and keeps everything 60 s. **Correctness:** records with TTL < 60 s are served after expiry (266 stale; `www.microsoft.com`, TTL 20 s, alone causes 189, and `www.cnn.com` 77). **Performance:** records with long TTLs (a day for `dns.google`) are re-fetched every 60 s (21 times instead of once), and every lookup is a linear scan. My cache stores `now + ttl` in a dict: 0 stale, 275 upstream vs. 325.
- The floor is **275**. Any correct cache must go upstream on the first query for each name, and on every query that arrives after the last fetched copy has expired — the TTL forbids answering from cache then. Fetching only when forced is optimal (an earlier fetch expires earlier, never later), so 275 is the minimum; 194 of it comes from the 20 s and 30 s CDN names, which no data structure can avoid.
