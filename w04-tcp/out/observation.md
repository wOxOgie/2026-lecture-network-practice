# Week 4 · Observation

## Task 1 · Reliable delivery
- I chose **selective repeat** (window 16, a timer per packet, receiver buffers out-of-order packets, at the cost of more receiver state). The case that forced it is reordering: with a receiver that only accepts the next expected packet (Go-Back-N style), every reordered packet is thrown away and resent, and the channels carried **1,346 packets instead of 597** (seed 246). Stop-and-wait also worked (604 packets) but needed **522 steps vs. 78**, because only one packet is ever in flight.
- Cost of reliability: 2,000 bytes = 250 data packets minimum, plus 250 ACKs. I sent **311 data + 286 ACKs = 597** (seed 246; 598 on seed 999), so **1.24× the minimum data packets and 1.19× overall**. The extra is almost entirely the 35 lost data packets plus the ACKs that were lost, each causing one retransmission.
- What broke first was **duplication**, in two ways. A receiver that writes every arrival gets duplicate packets (10 on seed 246) and the output is corrupted. A receiver that deduplicates but **does not ACK a duplicate** is worse: when the first ACK is lost, the sender retransmits forever and the receiver stays silent, a livelock that ran past the 200,000-step limit. The fix is to ACK every copy but write each sequence number only once.

## Task 2 · Handshake and throughput
- Capture `out/tcp.pcapng` (my laptop on `KT.Pascucci 5G` café Wi-Fi, filtered down to my 5 connections to speed.cloudflare.com 172.66.0.218, headers only). Handshake of the first connection: **frame 1 SYN, frame 2 SYN-ACK, frame 3 ACK** (port 50744). The ISNs are **client 1,051,786,843** and **server 1,422,020,476**, and every connection used different random ones. They are not 0 so that a delayed segment from an old connection on the same ports cannot fall inside the new connection's sequence space, and so that an off-path attacker cannot guess them to inject or reset the connection.
- SYN options: client **MSS 1460, window scale 8 (×256), SACK permitted**. The server answered MSS 1400, scale 13 (×8192), SACK permitted. In frame 3 the client advertised 255×256 = 65,280 B, which grew to **2047×256 = 524,032 B** during the transfer (Windows autotuning raised it to 1–2 MB on later connections). Bytes in flight on that connection peaked at 516,732 B but averaged **≈195 KB**. The bandwidth-delay product is only ≈75 Mb/s × ~9 ms ≈ **85 KB**, so most of the window was never needed. Unacknowledged data is capped by **min(cwnd, rwnd)**, and rwnd was reached only once, briefly, before autotuning raised it. So the limit was the sender's **cwnd**, which congestion control kept near what the bottleneck link could carry. The in-flight bytes above the BDP were sitting in a queue. For a 5 MB file, slow start also takes a large share of the 0.5 s transfer.
- Throughput (5 × 5 MB from speed.cloudflare.com): **`pascucci-wifi` median 75.45 Mb/s** (55.1–76.9, spread 29%), **handshake median 9.7 ms**. **`skt-hotspot` (phone tethering) median 19.41 Mb/s** (6.1–52.5, spread 239%), **handshake median 46.1 ms**. The hotspot's run 1 shows a 0.0 ms handshake because DNS took 181 ms and curl finished connecting before it reported the lookup as done. Without that run the median is ≈52 ms. Spread: on Wi-Fi only the first run was slow (TTFB 212 ms vs. ~70 ms after, from DNS/TLS/edge being cold), while the others agree within 5%. On the hotspot the cellular radio rate and the cell's scheduler change from second to second with signal and other users, so nothing repeats.
- **B5:** the hotspot's handshake (≈ one RTT) is ~5× the Wi-Fi's, and its throughput is ~4× lower. Within the hotspot runs the two move together: handshake **161 → 58 → 46 → 29 ms** went with **6.1 → 19.4 → 42.6 → 52.5 Mb/s**. The mechanism (§3.7) is **slow start with self-clocking**: cwnd grows only as ACKs come back, so it can double only once per RTT, and the sending rate ≈ cwnd / RTT. A 5 MB transfer spends most of its life ramping up, so a 5× longer RTT means a 5× slower ramp even if the radio could carry more. TTFB (TLS handshake + request, several RTTs) also rose from ~72 to ~173 ms before the first byte.

## Task 3 · Congestion control
- **R5:** The baseline has the most goodput (986.8 vs. my 948.5 per 1000 slots) because it never stops sending, but it gets there by keeping the queue almost always full (avg 8.8 of 10) and losing **37.4%** of what it sends (2,340 retransmissions). Every other flow on that link would wait behind those 8.8 packets and see its own packets tail-dropped. These are the two costs of congestion from §3.6: queuing delay that grows as the link nears capacity, and link capacity wasted on packets that are dropped and sent again. Goodput for one flow is not the goal on a shared link. Mine gets 96% of it with **2.0% loss and avg queue 4.3**.
- The link loses packets once the window reaches about pipe + queue + 1 ≈ **31**. I cut to 0.6 × that ≈ **19**, which is about the pipe itself (1 pkt/slot × 20 slots). The AIMD sawtooth then runs **≈19 → 31**, averaging ~25: the link never goes idle after a cut, and the queue only fills at the top. Growing at 0.5 packet per RTT (instead of 1) keeps the window in the low-queue range for longer. I also cut only **once per window**, because one overflow times out a whole burst of packets together. The bench reports loss only by timeout, where the textbook resets cwnd to 1 MSS. I cut to 0.6 instead, aiming at the goal of newer algorithms: keep the pipe full but the queue short.
- Making the backoff gentler raised goodput but cost queue and loss (once-per-window cut, +1/RTT): β=0.5 → **86%**, loss 2.1%, queue 3.1; β=0.7 → **97%**, 2.9%, 4.6; β=0.85 → **99%** but **5.1% loss and queue 7.2**, which fails both limits. Textbook-style control stays near 81–82%: resetting cwnd to 1 MSS on timeout gives 81%, and halving on every loss gives 82%, because each burst of timeouts halves the window several times.
